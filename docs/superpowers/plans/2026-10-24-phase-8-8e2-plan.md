# Plan: Phase 8 — 8e2 Link management
Author: Hao Nguyen. Status: building. Phase: 8. Sub-phase: 8e2
Spec: docs/superpowers/specs/2026-10-24-phase-8-design.md
Branch: phase-8-8e2-link-mgmt
BranchPoint: 7c7d9d7

Goal: the owner chooses the role (Xem / Sửa), the expiry (7 ngày / 30 ngày / Không hết hạn) and an optional label when creating a link. Each link shows its role and the remaining time ("còn 12 ngày"). Revoking a link asks for confirmation first. "Tắt chia sẻ" revokes every active link but keeps the room, so the owner can create new links later.

Facts (guard, branch phase-8):
- `CreateLinkRequest { role: ShareRole; label?: string; expiresIn: number | null }`
- `SHARE_EXPIRY_PRESETS` has keys '7d' | '30d' | 'never', mapped to ms or null.
- `ShareLink { token; tokenPrefix; roomId; role; label; createdAt; expiresAt: number | null; revokedAt: number | null }`
- The API's label limit is 120 characters.
- There is no revoke-all endpoint, only DELETE per prefix.
- ShareModal (168 lines, 17 tests) has a single "Tạo link xem" button, no role/expiry/label inputs, and revokes without confirmation.
- useShare (146 lines, 16 tests) exposes createLink(req) and revoke(prefix).

Decision: "Tắt chia sẻ" is implemented on the client as sequential DELETEs over the active links, so no new API endpoint is needed. A partial failure reports how many links remain.

### [ ] 8e2.2 — useShare.revokeAll and App wiring
FILES       apps/extension/src/app/collab/useShare.ts · apps/extension/src/app/collab/useShare.test.ts · apps/extension/src/app/App.tsx
INTERFACES  useShare's return gains `revokeAll: () => Promise<void>`. App passes `onRevokeAll={share.revokeAll}` to ShareModal (~App.tsx:571-584), using the prop added in 8e2.1.
BEHAVIOR    - revokeAll:
              - Take the active links (revokedAt null) from the current `links` state.
              - DELETE each one in sequence through the same request path as revoke, so it shares the owner auth, stale/gen guard and error mapping.
              - Mark each success as revoked locally, even if a later DELETE fails.
              - If any fail, throw/set error "Còn <n> link chưa thu hồi được".
              - Finish with refresh().
            - If not bound, it rejects with the existing 'Chưa bật chia sẻ'.
            - The room binding is kept: never clear `binding` and never delete the room record.
INVARIANTS  - apps/extension is the only layer that uses chrome.*.
            - The owner token travels only in the Authorization: Bearer header. It is never stored in the doc or logged.
            - Results from a doc that is no longer current must be discarded (the existing gen guard).
            - Existing useShare tests must pass unchanged.
TEST        pnpm --filter @md-reader/extension test src/app/collab/useShare.test.ts. Add these cases with the fetch mock:
            - 3 active links plus 1 revoked → 3 DELETEs in order, all links revokedAt set, binding unchanged
            - the second DELETE returns 500 → the error is "Còn 2 link chưa thu hồi được" and the first link is marked revoked
            - not bound → rejects
            Then pnpm --filter @md-reader/extension test (full count), pnpm --filter @md-reader/extension typecheck, pnpm -r typecheck.
COMMIT      feat(extension): Tắt chia sẻ = thu hồi mọi link, giữ phòng (8e2)
