# Plan: Phase 8 — 8e1 Role enforcement in the room
Author: Hao Nguyen. Status: built. Phase: 8. Sub-phase: 8e1
Spec: docs/superpowers/specs/2026-10-24-phase-8-design.md
Branch: phase-8-8e1-role-enforce
BranchPoint: d58792a

Goal: the Durable Object room enforces link roles. A connection whose token resolved to `view` can receive sync and awareness, but any sync step 2 or update it sends is dropped. The drop increments a counter, nothing is applied to the doc and nothing is broadcast. Awareness messages from every client are sanitized on the server, so a peer can only publish `{ name ≤40 chars, color = var(--peer-1..6), colorLight = the matching color-mix }`. This closes the remote `user.color` injection into y-codemirror cursor styles that 8d2 deferred.

Facts (guard, branch phase-8):
- `DocRoom extends YServer<Env>` (apps/api/src/room.ts:6). `onConnect` already stores `conn.setState({ role })` from the `x-mdr-role` header (default 'view'), and index.ts sets that header from the token's role after authorizeWs.
- y-partyserver 2.2.0 server: `onMessage(conn, msg)` → `handleMessage(conn, msg)`. It switches on the first varUint: 0 is sync (`readSyncMessage(decoder, encoder, this.document, connection, this.isReadOnly(connection))`), 1 is awareness (`applyAwarenessUpdate`, then broadcast to all). DocRoom does not override `isReadOnly`, `onMessage` or `handleMessage` today.

FILES       apps/api/src/protocol.ts (new) · apps/api/src/protocol.test.ts (new) · apps/api/package.json · pnpm-lock.yaml
INTERFACES  Add `lib0` and `y-protocols` as direct dependencies of apps/api, pinned to the exact versions already resolved in the lockfile (find them with `pnpm -r why lib0` and `pnpm -r why y-protocols`). Do not introduce a second copy.
            produces:
            export type MessageKind = 'step1' | 'step2' | 'update' | 'awareness' | 'other'
            export function classifyMessage(buf: Uint8Array): MessageKind
            export const PEER_COLOR_RE: RegExp   // /^var\(--peer-[1-6]\)$/
            export function sanitizeUser(user: unknown): { name: string; color: string; colorLight: string } | null
            export function sanitizeAwarenessMessage(buf: Uint8Array): Uint8Array | null
BEHAVIOR    - classifyMessage reads the outer varUint:
              - 0 → read the inner sync type varUint: 0 is 'step1', 1 is 'step2', 2 is 'update', anything else is 'other'.
              - 1 → 'awareness'.
              - Anything else, including an empty or truncated buffer, is 'other'. It never throws.
            - sanitizeUser returns null unless user is a plain object.
              - name: `typeof name === 'string'` ? trimmed and sliced to 40 : ''. An empty result becomes 'Ẩn danh'.
              - color: kept only if it matches PEER_COLOR_RE, otherwise 'var(--peer-1)'.
              - colorLight: always recomputed as `color-mix(in srgb, ${color} 20%, transparent)`.
            - sanitizeAwarenessMessage takes a full message (outer 1 + varUint8Array awareness update) and returns null if it is not an awareness message or fails to decode.
              - Decode the awareness update entries (clientID, clock, JSON state string, per the y-protocols awareness encoding).
              - For each entry: a state of 'null' (removal) stays as is. Otherwise JSON.parse it; on a parse failure, drop the entry. Replace `state.user` with `sanitizeUser(state.user)`, deleting `user` if that returns null.
              - Keep other top-level fields only if they are named `cursor` (y-codemirror's selection), and drop everything else.
              - Re-encode in the same format, with the outer type 1.
INVARIANTS  - apps/api runs on Cloudflare Workers: no document, window or chrome.*, and no Node-only modules.
            - Raw tokens are never logged.
            - Pure functions only. No I/O, and no state beyond the RegExp constant.
TEST        pnpm --filter @md-reader/api test src/protocol.test.ts. Build messages with the real encoders (y-protocols sync writeSyncStep1/writeUpdate, and awareness encodeAwarenessUpdate on a real Awareness, wrapped with lib0 encoding plus the outer type) and check that:
            - classifyMessage gives step1, step2, update and awareness for the real messages, 'other' for [] and [7], and does not throw on a truncated buffer.
            - sanitizeUser handles a valid user unchanged (colorLight recomputed), color 'red;background:url(x)' → 'var(--peer-1)', name {} → 'Ẩn danh', a name over 40 chars capped, and a non-object → null.
            - sanitizeAwarenessMessage, on an update holding one state with a malicious color plus an extra field `token: 'x'`, decodes (via applyAwarenessUpdate into a fresh Awareness) to user.color 'var(--peer-1)', no token field, and the cursor field kept. A removal entry (null state) survives. Garbage returns null.
            Then pnpm --filter @md-reader/api test (full count) and pnpm --filter @md-reader/api typecheck.

### [x] 8e1.2 — DocRoom enforces roles and sanitizes awareness
FILES       apps/api/src/room.ts · apps/api/src/room.test.ts (new)
INTERFACES  consumes `classifyMessage` and `sanitizeAwarenessMessage` from './protocol' (8e1.1).
            DocRoom gains:
            - `droppedWrites: number` (public, starts at 0)
            - `isReadOnly(conn: Connection): boolean`, which returns `(conn.state as { role?: string } | null)?.role !== 'edit'`
            - an override of `handleMessage(conn, message)`
BEHAVIOR    - First, read y-partyserver's dist/server/index.js and confirm what readSyncMessage does with the readOnly flag for step2 and update. Report it in NOTES.
            - handleMessage(conn, message): if message is a string, call super.handleMessage. Otherwise take bytes = Uint8Array view of the ArrayBuffer/Uint8Array, and k = classifyMessage(bytes).
              - k is 'step2' or 'update', and isReadOnly(conn): `this.droppedWrites++`, then return without calling super. Nothing is applied and nothing is broadcast.
              - k is 'awareness': s = sanitizeAwarenessMessage(bytes). If s is null, return (drop). Otherwise call super.handleMessage(conn, s), passing it in the type super expects.
              - Otherwise call super.handleMessage(conn, message).
            - No logging of message contents or tokens. A single `console.warn('mdr: dropped write from view connection')` is allowed at most once per connection, and is optional.
INVARIANTS  - apps/api runs on Workers. A role comes only from the x-mdr-role header that index.ts sets after authorizeWs; a client can never choose its own role.
            - The default for a missing role is read-only.
            - Edit connections behave exactly as before.
            - Persistence (onLoad/onSave) is unchanged.
TEST        pnpm --filter @md-reader/api test src/room.test.ts.
            - Instantiate DocRoom with the existing test stub for cloudflare:workers (apps/api/test/cloudflare-workers-stub.ts; check vitest config aliases), or else test a thin subclass with super.handleMessage spied/stubbed. Real Durable Object storage is not needed.
            - Cases:
              - a view connection sending an update → droppedWrites is 1, super.handleMessage is not called, and room.document has no text
              - an edit connection sending the same update → super is called and the text appears in room.document
              - a view connection sending step1 → super is called (it can still sync down)
              - an awareness message with a malicious color from any role → super receives a sanitized buffer with user.color 'var(--peer-1)'
              - garbage binary → dropped without throwing
              - a missing state or role → treated as read-only
